End-to-End GitOps Continuous Delivery Pipeline

A hands-on lab that removes manual kubectl apply from the release path entirely. Git is the single source of truth: a commit that changes pod density is detected by Argo CD and reconciled into a running Kubernetes cluster — no operator in the loop.

01 / Architecture

System topology

Three cooperating planes: authoring and version control on the left, the GitOps reconciliation loop in the middle, and observability on the right.

PLANE 01

Authoring & version control

Source and infrastructure manifests live together, so an application change and the intent to deploy it are one atomic commit.

  • VS Code on Ubuntu via WSL2
  • index.html + Dockerfile
  • k8s/deployment.yaml, service.yaml

PLANE 02

GitOps reconciliation

Argo CD polls the repository, diffs desired state against live state, and applies the delta. Drift is corrected without human intervention.

  • Watches portfolio-01 @ HEAD
  • Path k8s → namespace default
  • Auto-sync + self-heal enabled

PLANE 03

Runtime & observability

The workload runs on a local cluster. Metrics collection and dashboards are the explicitly scoped next phase of this lab.

  • Docker Desktop Kubernetes
  • 4 replicas behind a NodePort service
  • Prometheus + Grafana (planned)

02 / Workflow

Commit-to-running pipeline

Four stages, one direction of flow. Nothing after stage two is executed by hand.

01 / Build

Containerise

The static site is baked into an nginx:alpine image and tagged heinsitt/portfolio:latest.

02 / Publish

Push to registries

Image layers go to Docker Hub; the manifest change is committed to the portfolio-01 repository.

03 / Detect

Argo CD reconciles

The controller compares Git against the cluster, reports OutOfSync, then applies the difference.

04 / Enforce

Kubernetes self-heals

The ReplicaSet maintains the declared pod count. Deleted pods are replaced automatically to match desired state.

03 / Implementation

How each layer is declared

Every artefact below is a file in Git, not a cluster mutation performed from a shell.

Image build & distribution

A two-instruction Dockerfile serves the static site through nginx, keeping the runtime image small and the build reproducible.

Dockerfile 
FROM nginx:alpine
COPY ./ /usr/share/nginx/html
Push to Docker Hub 
$ docker build -t heinsitt/portfolio:latest .
$ docker push heinsitt/portfolio:latest

Declarative workload & declarative scaling

Capacity is a number in a YAML file. Changing replicas: 2 to replicas: 4 and pushing the commit is the entire scaling operation.

k8s/deployment.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: portfolio-deployment
spec:
  replicas: 4
  selector:
    matchLabels:
      app: portfolio
  template:
    metadata:
      labels:
        app: portfolio
    spec:
      containers:
      - name: portfolio
        image: heinsitt/portfolio:latest
        ports:
        - containerPort: 80
Auto-sync Self-heal ReplicaSet

04 / Verification

Proof, not claims

After the manifest commit, the cluster reported four ready pods and Argo CD reported Synced to HEAD with health Healthy.

Post-sync cluster state

Replica count went from two to four with no manual rollout command — the extra pods were created by Argo CD applying the new manifest.

Service exposure

A NodePort service fronts the replica set. The app was verified in a browser through a port-forward, confirming end-to-end delivery.

kubectl 
$ kubectl get svc
NAME                TYPE        CLUSTER-IP     PORT(S)
kubernetes          ClusterIP   10.96.0.1      443/TCP
portfolio-service   NodePort    10.96.90.246   80:32284/TCP

$ kubectl port-forward svc/portfolio-service 8081:80
Forwarding from 127.0.0.1:8081 -> 80
Forwarding from [::1]:8081 -> 80
Handling connection for 8081

Scope note. This lab runs on a local single-node cluster (Docker Desktop Kubernetes). Port-forwarding is a verification mechanism here, not a production ingress strategy — a LoadBalancer controller or Ingress is the correct next step for public exposure.

07 / Scope

Delivered vs. next phase

Deliberately separating what this lab proves from what it defers keeps the claim honest.

Completed

Automated delivery loop

  • Container image built and published
  • Declarative Deployment and Service in Git
  • Argo CD auto-sync with health reporting
  • Replica scaling committed, not applied
  • Self-healing verified against desired state
  • Application reached in browser via port-forward

Planned

Observability plane

  • Prometheus metrics collection in the cluster
  • Grafana dashboards for pod and node health
  • Alerting rules on replica and restart anomalies
  • Ingress controller replacing port-forward
